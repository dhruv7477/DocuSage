Part 1: Business Case Study

Executive Summary

Every organization sits on a mountain of documents: contracts, policies, manuals, reports. The knowledge inside them is locked away, findable only by whoever remembers which file it's in. DocuSage turns that pile into a private, conversational expert: upload your documents, ask questions in plain English, and get clear answers backed only by your own files, with the exact source passage shown as proof. It's the convenience of a chatbot without the two things that make generic AI risky for business: making things up, and leaking your data.

Business Challenges

Before DocuSage, finding answers inside documents meant:

  • Hours of manual hunting. Staff scrolled through long PDFs to find one clause or figure.
  • Knowledge bottlenecks. Only a few experts knew where things lived; when they were out, work stalled.
  • Risky shortcuts. Public AI tools could invent confident-sounding but wrong answers, and pasting confidential documents into them exposed sensitive data.
  • No trust, no audit trail. Even when an answer was found, there was no easy way to prove where it came from.

Solution Approach

DocuSage reads your documents once, indexes them, and then answers questions about them on demand. Behind the simple chat box is a short relay of focused steps, like a well-run research desk: one step works out what you're really asking, another digs up the most relevant evidence, another writes the answer, and a final check confirms it cites real sources. Only the writing (and summarizing) uses a language model; the routing is rules first, and the final check is a program, not another AI call. Every answer is grounded in your documents and cited, and if the documents don't contain the answer, DocuSage says so instead of guessing. Everything stays in your private, walled-off workspace.

The Workflow (Simplified)

            ┌──────────────────────── DocuSage ────────────────────────┐
  Upload ─▶ │  📥 Librarian: reads · splits · files every document      │
            └───────────────────────────┬───────────────────────────────┘
                                         │  (indexed & ready to search)
                                         ▼
  Question ─▶ 🧭 Router ─┬─ a question  ─▶ 🔎 Researcher ─▶ ✍️ Writer ──┐
                         ├─ a summary   ─▶ 📚 Summarizer ───────────────┤─▶ ✅ Citation check ─▶ 📎 Cited Answer
                         └─ small talk  ─▶ 💬 Quick reply ──────────────┘

Think of it as a relay, each step doing one job well:

  • 📥 The Librarian reads each uploaded file (PDF, Word, plain text, Markdown or HTML), breaks it into bite-sized passages, and files them so they can be found instantly later. This runs in the background, with live progress in the app.
  • 🧭 The Router decides what you actually want: a specific answer, a whole-document summary, or just a friendly hello. Clear cases are recognized by rules at no cost; an AI classifier can be switched on for harder ones.
  • 🔎 The Researcher searches your documents two ways at once (by meaning and by keyword), re-ranks the results to surface the best evidence, and declines if nothing relevant turns up.
  • ✍️ The Writer composes an answer using only that evidence, attaching citations that link back to the exact page and passage.
  • 📚 The Summarizer, for an overview request, reads the whole document in sections and distills an executive summary. A deployment can switch summaries off to save model capacity.
  • ✅ The Citation check is a program that verifies every citation points to a real source and that the answer kept the "decline when unsure" promise.

The result streams back live, with a "Check source" preview showing a snapshot of the actual document page with the passage highlighted, so you can trust, and verify, in one glance.

Technical Implementation Plan

  • Architecture: a FastAPI (Python) backend with a React/TypeScript front end; a ChatOrchestrator routes each turn to the right step rather than relying on one giant prompt.
  • Document pipeline: uploads are parsed, chunked, embedded, and stored in a Qdrant vector database; originals live in S3-compatible object storage. Indexing runs in a background worker.
  • Retrieval: dense (semantic) and keyword search fused with Reciprocal Rank Fusion, then a cross-encoder re-ranker with a confidence threshold for abstention, the anti-hallucination safeguard.
  • Answering: the model streams a grounded, cited response; a programmatic validator (no extra AI cost) checks citations. Models are pluggable: a local model through Ollama, OpenAI or any OpenAI-compatible service such as Groq, or a vLLM server.
  • Privacy & multi-tenancy: each workspace is isolated, with its own vector collection and storage prefix, and every search is filtered by user.
  • Operations: separate models for chat and summarization to balance speed and cost; rate limits and quotas for public deployments; automated tests, dependency and container scanning, static analysis and a web security scan on every change.

One platform, a few focused steps, and a simple promise: answers you can trust, sourced from documents you own.

Part 2: Technical Deep Dive

For engineers and technical stakeholders.

1. System at a Glance

DocuSage is a multi-tenant, retrieval-augmented-generation (RAG) platform: users upload documents and get cited, document-grounded answers through a chat interface.

  • Backend: FastAPI + SQLAlchemy (async), entry point src/main.py:create_app().
  • Frontend: React 18 + TypeScript + Vite, SSE-driven chat UI.
  • Datastores: PostgreSQL (relational), Qdrant (vectors), Redis (Celery broker, revoked-token list, rate-limit counters), S3-compatible object storage for the original files (SeaweedFS in the compose files, or Amazon S3).
  • Async work: a Celery worker runs the ingestion pipeline.
  • Models: pluggable LLM providers (Ollama, OpenAI or any OpenAI-compatible API such as Groq, vLLM) and embedding providers (BGE in-process, OpenAI) selected at runtime through config factories.

Backend layering: thin route handlers (src/api/v1/) → business logic (src/services/) → retrieval (src/retrieval/) → ingestion (src/ingestion/) → provider and store abstractions (src/providers/, src/vector_store/) → cross-cutting concerns (src/core/: exceptions, JWT + bcrypt security, structured logging, rate limiting, audit).

2. Document Ingestion Pipeline

Upload → object storage (raw file) + Document row (PENDING)
       → Celery task: parse → chunk → embed → Qdrant upsert
       → status transitions → COMPLETED
  • Parsers handle PDF, DOCX (and DOC), TXT, Markdown and HTML.
  • Chunker creates overlapping passages and preserves heading context (heading_path) for precise citations.
  • Embedding (default BAAI/bge-small-en-v1.5, 384 dimensions) vectorizes each chunk.
  • Qdrant upsert stores vectors + payload (document_id, user_id, page_number, text, heading_path, offsets) and a full-text payload index for keyword search.
  • Progress and failures are persisted on the Document row and shown live; a periodic sweep fails documents stuck in processing.

3. Retrieval Pipeline (src/retrieval/)

  1. Query understanding: standalone-question rewriting (gated by an anaphora regex and prior turns) and optional HyDE (a recall booster, off by default).
  2. Hybrid retrieval: concurrent dense and keyword searches fused with Reciprocal Rank Fusion (RRF); all reads filtered by user_id and workspace.
  3. Reranking + abstention: a cross-encoder (default cross-encoder/ms-marco-MiniLM-L-6-v2, configurable) scores (query, candidate) pairs; scores are sigmoid-normalized to [0,1] so one abstention_threshold decides whether to answer at all.

Flow: hybrid retrieve (about top 50) → rerank → top-k → grounded prompt.

4. Orchestration (as built)

The chat path implements the routing workflow from Anthropic's Building Effective Agents: classify, then dispatch to a specialized path. ChatOrchestrator.prepare() is the "prepare" half of a turn.

  • QuestionAnalyzer (router): rules first, at no cost. Greetings get a fixed reply, summary requests go to the summarizer, everything else is rag_query. An optional small JSON-mode LLM classifier (ROUTER_USE_LLM, off by default) is fail-open: any error falls back to rag_query.
  • off_topic: a short reply, pseudo-streamed, no retrieval.
  • doc_summary: DocSummaryService map-reduce; oversized documents are split into parts, each streamed (so the read timeout only has to cover the time to the first token), then reduced into a streamed executive summary. DOC_SUMMARY_ENABLED=false sends summary requests down the RAG path with a warning.
  • rag_query: RAGService, query understanding → hybrid retrieve → rerank → prompt_builder assembles the grounded prompt → token stream. If nothing is relevant enough, the turn is declined with a fixed reply.

The orchestrator returns a StreamPlan (token iterator + sources, confidence, abstained flag, citation legitimacy). Transport is SSE (/chat/{id}/stream) through a producer/queue with an 8-second keepalive heartbeat. After the last token, answer_validator runs programmatically (no second LLM pass) to verify citations and the abstention contract; messages persist to PostgreSQL. Citations link to a PyMuPDF-rendered page image with the cited passage highlighted (optionally cropped): the UI's "Check source" preview.

5. Multi-Tenancy, Security, Configuration

  • Isolation: per-workspace Qdrant collection ({prefix}_ws_{workspace_id}), every query also filtered by user_id, workspace-prefixed storage paths; tested against a real Qdrant.
  • Auth: JWT (PyJWT) + bcrypt; dependency guards; audit log.
  • Abuse controls: per-IP and per-user rate limits, per-user quotas and an optional site-wide daily question budget, all off by default for self-hosted installs.
  • Config: a single Pydantic BaseSettings source; models swappable per role (chat, router, summarization).
  • Quality: an eval API and service track RAG quality and regressions. CI runs ruff, unit and integration tests against real services, the frontend, and the demo stack end to end; separate workflows run dependency audits, CodeQL, a secret scan, image scans and an OWASP ZAP scan on every pull request.

6. Reference Architecture: Orchestration with LangGraph

Note: today the orchestration is a purpose-built async controller (ChatOrchestrator + producer/queue SSE loop) that already behaves like a small state machine. This section shows how we would express the same workflow in LangGraph, and why we'd choose it over plain LangChain as the agent logic grows.

The workflow as a graph

LangGraph models the app as a StateGraph: a typed shared state flows through nodes connected by edges, including conditional and cyclic ones.

              ┌─────────────┐
   START ───▶ │  router     │  (QuestionAnalyzer)
              └──────┬──────┘
        off_topic │  doc_summary │  rag_query
        ▼          ▼              ▼
   ┌─────────┐ ┌───────────┐ ┌──────────────┐
   │ decline │ │ summarize │ │ understand_q │
   └────┬────┘ │ (map→     │ └──────┬───────┘
        │      │  reduce)  │        ▼
        │      └─────┬─────┘   ┌──────────┐
        │            │         │ retrieve │ (hybrid + RRF)
        │            │         └────┬─────┘
        │            │              ▼
        │            │         ┌──────────┐  below threshold
        │            │         │ rerank   ├──────────────▶ decline
        │            │         └────┬─────┘
        │            │              ▼
        │            │         ┌──────────┐
        │            │         │ generate │
        │            │         └────┬─────┘
        └────────────┴──────────────┤
                                     ▼
                              ┌────────────┐  citations invalid →
                              │  validate  ├──── (loop) ────▶ regenerate
                              └─────┬──────┘
                                    ▼
                                   END

Shared state (typed) carries: query, chat_history, intent, enriched_queries, candidates, reranked, confidence, answer, sources, abstained. The mapping to existing code is nearly one to one: router→QuestionAnalyzer; understand_q/retrieve/rerank→src/retrieval/*; generate→RAGService+prompt_builder; summarize→DocSummaryService (LangGraph's Send API expresses map fan-out and reduce join); validate→answer_validator, with a conditional edge that could loop back to generate. Today the validator corrects the answer in place and does not retry.

What LangGraph adds: first-class conditional routing and cycles; per-node event streaming (maps onto our SSE events); checkpointing and durable state (resumability, human-in-the-loop, time-travel debugging); and graph-level observability (LangSmith tracing).

Why LangGraph over LangChain (for orchestration)

They're complementary: LangGraph is built by the LangChain team and uses LangChain components inside nodes. The difference is control flow:

ConcernLangChain (chains / LCEL)LangGraph
Control flowLinear pipelines / DAGs (A→B→C)Graph with branches, loops, conditionals
Branch by intentPossible but rigid (RouterChain)Native conditional edges
Cyclic flows (retry/refine)Hard: chains terminate forwardFirst-class: designed for cycles
Shared evolving stateImplicit, hard to inspectCentral typed state
Pause / resume / human-in-loopNot built inCheckpointers make it native
Streaming partial progressFinal-output orientedPer-node event streaming
Map-reduce fan-outManualSend API

Bottom line for DocuSage: the flow is not a straight pipeline. It branches on intent, could loop (validate→regenerate; retrieve→re-query on low confidence), fans out and in for summarization, and streams progress mid-flight. These are exactly the patterns LangChain's chain abstraction strains to express and LangGraph models directly. LangChain stays the right choice for the building blocks (model and embedding adapters, retrievers, parsers); LangGraph is the right choice for the orchestration that wires them into a stateful, conditional graph, replacing bespoke plumbing with a standardized, observable, resumable graph that is easy to extend (add a node and edges for a "clarifying question" or "tool use" step).

7. Deployment & Operations

  • Local development: Docker Compose for Postgres, Qdrant, Redis, SeaweedFS and Ollama; the API, Celery worker and Vite run on the host.
  • Public demo: the whole stack on one small VM (linux/arm64) behind Caddy (automatic HTTPS, security headers), with Groq as the hosted LLM through the OpenAI-compatible provider.
  • Migrations: Alembic (alembic upgrade head), run when the API container starts.
  • CI: lint → unit and integration tests → frontend → image builds for amd64 and arm64 → demo stack end to end, plus the security workflows. Nothing is pushed to a registry.
  • Tuning levers: model selection per role, retrieval top-k and abstention threshold, chunk size and overlap, summary budgets, rate limits and quotas, all through environment configuration.
